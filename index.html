CPU Cache Write Policy: Write-through vs Write-back (and Write-Allocate)

Why this topic matters

Cache write policy directly affects latency, memory bandwidth pressure, and multi-core correctness. In real systems (especially low-latency trading, real-time analytics, and game/graphics engines), a poor mental model of “where the latest value lives” leads to incorrect assumptions about performance, false sharing, and device/DMA interactions.

Getting this right also helps you reason about profiling results and why “a simple store” can become expensive under contention or coherence traffic.

One-sentence takeaway

Write-through updates cache and memory on every store, while write-back updates cache now and writes to memory later (on eviction/flush), trading simplicity for much higher performance.

Core concept explained

A write policy defines what happens when the CPU stores to an address that is (typically) already cached.

Write-through (直写 / 写穿)

When the CPU writes a value:

  1. The cache line is updated.
  2. The same write is immediately propagated to the next level (eventually RAM).

This keeps main memory up-to-date at all times, which simplifies reasoning about “what’s in RAM,” but it increases write traffic and can stall if the write path is saturated (even with a write buffer).

Write-back (回写)

When the CPU writes a value:

  1. The cache line is updated.
  2. The cache line is marked dirty (meaning: “newer than memory”).
  3. Memory is updated later, typically when the line is evicted (replaced) or explicitly flushed.

This reduces external memory traffic dramatically because multiple stores to the same cache line become one eventual writeback. The cost is complexity: the most recent value may live only in a private cache, not in RAM.

Key mental model: with write-back, RAM can be stale; the “truth” may be in a core’s cache until eviction/flush/coherence actions occur.

Important add-on: Write-allocate vs No-write-allocate (applies on write miss)

Write policy is often discussed alongside what happens on a write miss (the line is not in cache yet):

  • Write-allocate (fetch-on-write): on miss, fetch the whole cache line into cache, then perform the store in cache.
    Common pairing: write-back + write-allocate.
  • No-write-allocate (write-around): on miss, do not bring the line into cache; write directly to lower level.
    Common pairing: write-through + no-write-allocate (especially for streaming stores).

So “write-through vs write-back” answers when memory is updated, while “allocate vs not” answers whether a miss pulls the line into cache.

How it is used in practice

Why CPUs favor write-back

Most modern CPU data caches are write-back because it:

  • Minimizes memory bandwidth usage.
  • Improves store throughput by absorbing writes in cache.
  • Exploits locality: many real workloads update nearby data repeatedly.

This is especially important on multi-core systems where external writes also trigger coherence actions; writing less to memory generally reduces system-wide pressure.

When write-through shows up

Write-through can appear:

  • In some embedded designs where simplicity and predictability matter more than peak throughput.
  • In specific cache levels or special-purpose caches (design dependent).
  • As a conceptual model for certain buffering layers.

In general-purpose high-performance CPUs, you should assume write-back unless you are told otherwise.

Practical consequences for C++ engineers

Stores often “look cheap” in source code, but can become expensive if they cause:

  • Cache line bouncing (false sharing).
  • Evictions of dirty lines (writeback bursts).
  • Saturation of write buffers or the memory subsystem.

Memory-mapped I/O (MMIO) or DMA scenarios require careful handling (flush/invalidate or platform-provided coherence), because write-back means RAM may not reflect the latest data.

Common pitfalls or misconceptions

  1. Misconception: “After I write, RAM has the new value.”
    Reality: Under write-back, RAM may not be updated until eviction/flush. The latest value might be in L1/L2 (or another cache level) with the line marked dirty.

  2. Misconception: “Write policy is the same as cache coherence.”
    Reality: Write policy decides when lower memory is updated; coherence (MESI/MOESI-like protocols) decides how multiple cores see consistent values and who owns/invalidates lines. You can have coherent write-back caches where other cores still see your updates via coherence, even though RAM is stale.

  3. Misconception: “Write-through is always slower.”
    Reality: Write-through often increases traffic, but performance depends on workload and buffering. With strong write combining / write buffers and streaming patterns, the gap can narrow. Still, write-back typically wins for general workloads with temporal locality.

Practical engineering perspective

In practice, strong understanding typically includes:

  • A correct definition of write-through and write-back.
  • The notion of a dirty bit and eviction-triggered writeback.
  • The main trade-off: simplicity vs bandwidth/performance.
  • Awareness that “RAM can be stale,” plus a brief mention of DMA/MMIO implications or flush/invalidate operations (no need to go deep unless asked).

Signals of strong understanding:

  • You mention write buffers, eviction behavior, and why write-back reduces traffic.
  • You separate write policy from coherence.
  • You optionally add write-allocate vs no-write-allocate on write miss.

Common signs of incomplete understanding:

  • “Write-back means it writes later, write-through writes now” with no mention of dirty lines/eviction.
  • Claiming memory is always updated on a store.
  • Confusing write policy with coherence or memory ordering.

Summary for practical use

  • Core idea: Write-through writes cache + memory immediately; write-back writes cache now and writes memory later (on eviction/flush).
  • Key behaviour: Write-back uses dirty cache lines; RAM may be stale until writeback occurs.
  • Main trade-off: Write-through = simpler consistency model but higher bandwidth/latency; write-back = higher performance but more complex interactions (DMA/MMIO, eviction effects).
  • One common pitfall: Assuming a store immediately updates RAM under write-back.
  • One practical guideline: Assume modern CPUs use write-back; optimize to reduce dirty evictions and false sharing (cache line contention), and be cautious with DMA/MMIO without proper cache maintenance.

Personal takeaway

Write policy reinforces the idea that memory is a hierarchy rather than a single, uniform place. In performance-critical systems, stores should be thought of as operations that primarily modify cache state first, with updates to main memory occurring later depending on eviction, flush, and coherence behavior.

This mental model has made me more deliberate about cache-line locality, false sharing avoidance, and understanding the correctness boundaries around device I/O and shared-memory communication in real systems.
